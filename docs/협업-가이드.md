# 공동 작업 가이드

조원 2~3명이 같이 코드를 고칠 때 보는 문서입니다.

> **Git 을 잘 몰라도 됩니다.** 명령어 네 개와 "내 파일만 건드린다" 규칙만 지키면
> 됩니다. 나머지는 GitHub 가 자동으로 검사해 줍니다.

---

# 1. 처음 한 번만 (각자 30분)

## 1-1. 저장소 받기 — 조원

**먼저 저장소 주인이 초대해야 합니다.** (아래 1-2 참고)

1. [Node.js](https://nodejs.org) 에서 **LTS** 버전 설치
2. [Git](https://git-scm.com/downloads) 설치 (설치 중 선택지는 전부 기본값)
3. 작업할 폴더를 정하고, 그 폴더에서 터미널을 엽니다
   - 윈도우: 폴더에서 마우스 오른쪽 → **Git Bash Here** 또는 **터미널에서 열기**
4. 아래를 차례로 칩니다

```bash
git clone https://github.com/min52185/remicon-match.git
cd remicon-match
npm install
```

5. 팀 채팅방에서 받은 내용을 `.env.local` 파일로 만들어 **프로젝트 맨 위 폴더**에 둡니다
6. 실행해 봅니다

```bash
npm run dev
```

7. <http://localhost:3000> 이 열리면 성공입니다

> **키를 아직 못 받았어도 괜찮습니다.** `npm run dev` 는 키 없이도 돌아갑니다.
> 로그인 없는 시연 모드가 되고, 지도는 대체 지도로, 이동시간은 직선거리 근사로
> 바뀝니다. 화면에 어느 쪽인지 표시됩니다.

## 1-2. 조원 초대하기 — 저장소 주인

1. <https://github.com/min52185/remicon-match> 접속
2. 위쪽 **Settings**
3. 왼쪽 **Collaborators**
4. **Add people** → 조원의 GitHub 아이디 또는 이메일
5. 조원은 메일로 온 초대를 **수락**해야 합니다

## 1-3. 키 나눠주기 — 저장소 주인

`.env.local` 파일의 내용을 **팀 채팅방으로만** 보냅니다.

> ⚠️ **저장소에 올리면 안 됩니다.** 공개 저장소라 키가 그대로 남습니다.
> 이미 올렸다면 지우는 것만으로는 부족하고 **키를 새로 발급**해야 합니다.
> (`.gitignore` 에 걸려 있어서 실수로 올라가지는 않습니다.)

## 1-4. Supabase 접근 — 필요한 사람만

DB 를 직접 봐야 하는 사람만 초대합니다. 대부분은 필요 없습니다.

1. Supabase 대시보드 → 왼쪽 아래 **조직 이름** → **Team**
2. **Invite** → 조원 이메일
3. 초대는 **24시간 안에** 수락해야 합니다

# 2. 담당 나누기 — 가장 중요합니다

**같은 파일을 두 사람이 동시에 고치면 충돌이 납니다.** Git 을 모르면 충돌을 푸는
것이 제일 어렵습니다. 그래서 애초에 겹치지 않게 나눕니다.

## 2-1. 화면별로 나누는 것이 가장 안전합니다

| 담당 | 폴더 | 안에 있는 것 |
| --- | --- | --- |
| **현장 담당** | `app/site/` | 현황 · 주문 · 즐겨찾기 · AI 배분 · 추적 · 납품서 · 현장 등록 |
| **공장 담당** | `app/plant/` | 출하 현황 · 주문 관리 · 배차 · 공장 등록 |
| **기사 담당** | `app/driver/` | 내 배송 · GPS · 사진 |

이 세 폴더는 서로를 건드리지 않습니다. 각자 자기 폴더 안에서는 마음껏 고쳐도
충돌이 나지 않습니다.

## 2-2. 공용 파일 — 고치기 전에 말하기

아래는 **여러 화면이 같이 쓰는 파일**입니다. 두 사람이 동시에 고치면 충돌합니다.

| 파일 | 무엇 | 고치기 전에 |
| --- | --- | --- |
| `lib/rules.ts` | 시방 수치·판정 규칙 | 채팅방에 "rules 고칠게요" |
| `lib/types.ts` | 자료 모양 | 채팅방에 알리기 |
| `components/` | 화면 공용 부품 | 채팅방에 알리기 |
| `lib/store/` | 저장소 (DB 읽고 쓰기) | 채팅방에 알리기 |
| `app/globals.css` | 색·글꼴·공통 모양 | 채팅방에 알리기 |
| `supabase/migrations/` | DB 구조 | **반드시** 알리기 (아래 2-3) |

> 한 줄만 고치는 것도 알리세요. 충돌은 줄 수와 상관없이 납니다.

## 2-3. DB 를 바꿀 때 — 규칙이 하나 더 있습니다

`supabase/migrations/` 에 SQL 파일을 새로 만들 때는:

1. **기존 파일을 고치지 않습니다.** 이미 실행한 SQL 을 고쳐도 DB 는 안 바뀝니다
2. **다음 번호**로 새 파일을 만듭니다 — 지금은 `0010` 까지 있으니 `0011_...sql`
3. 번호가 겹치지 않게 **채팅방에 먼저 알립니다** ("0011 쓸게요")
4. 만든 사람이 Supabase SQL Editor 에서 **직접 실행**합니다
5. 채팅방에 "0011 돌렸습니다" 라고 알립니다 — 다른 사람도 돌려야 할 수 있습니다

# 3. 매일 쓰는 명령어 — 네 개뿐입니다

작업할 폴더에서 터미널을 열고 씁니다.

## 3-1. 작업 시작할 때

```bash
git pull
```

다른 사람이 올린 것을 받아옵니다. **작업 전에 반드시 한 번.**
이걸 안 하면 나중에 충돌이 납니다.

## 3-2. 작업이 끝났을 때

```bash
git add .
git commit -m "무엇을 왜 바꿨는지"
git push
```

세 줄을 차례로 칩니다.

| 명령 | 뜻 |
| --- | --- |
| `git add .` | 고친 파일을 전부 담는다 |
| `git commit -m "..."` | 담은 것에 설명을 붙여 저장한다 |
| `git push` | GitHub 에 올린다 |

## 3-3. 커밋 메시지 쓰는 법

**무엇을 왜 바꿨는지** 적습니다. 나중에 "왜 이렇게 했지?" 할 때 답이 됩니다.

| 나쁨 | 좋음 |
| --- | --- |
| `수정` | `기사 화면에서 도착 시각이 안 보이던 것 수정` |
| `기능 추가` | `공장별 단가 입력 추가 — 정산에 쓰려고` |
| `asdf` | `주문 취소 버튼이 두 번 눌리던 것 막음` |

## 3-4. 올리기 전에 한 번 확인

```bash
npm test
```

**통과해야 올립니다.** 실패하면 무언가를 망가뜨린 것입니다.

> `npm run build` 를 돌릴 때는 **개발 서버를 먼저 끄세요**(Ctrl+C).
> 둘 다 `.next` 폴더를 써서 켜 둔 채 빌드하면 캐시가 깨집니다.

올릴 때마다 GitHub 가 **타입 검사 · 테스트 · 빌드**를 돌립니다.

1. <https://github.com/min52185/remicon-match> 에서 **Actions** 탭

| 표시 | 뜻 | 할 일 |
| --- | --- | --- |

> ❌ 가 뜨면 **배포본도 그 상태로 나갑니다.** 발표 전에 빨간 X 가 있으면 안 됩니다.

# 5. 규칙 — 이것만 지켜 주세요

`CLAUDE.md` 에 전체 규칙이 있지만, 자주 걸리는 것만 추립니다.

| 규칙 | 왜 |
| --- | --- |
| **`.env.local` 을 커밋하지 않는다** | 공개 저장소입니다. 키가 그대로 남습니다 |
| **시방 수치는 `lib/rules.ts` 에만** | 90분·25℃·6m³ 같은 값을 화면에 직접 쓰지 않습니다. 기준이 바뀔 때 한 군데만 고치게 합니다 |
| **가정치에는 `// [가정]` 주석** | 무엇이 확실하고 무엇이 어림인지 코드에서 구분됩니다 |
| **기능을 만들면 테스트도** | `tests/` 에 같이 넣고 `npm test` 를 통과시킵니다 |
| **새 DB 테이블에는 RLS** | 권한을 안 걸면 남의 회사 자료가 보입니다 |
| **`SUPABASE_SERVICE_ROLE_KEY` 금지** | 권한 검사를 통째로 무시하는 키입니다 |
| **개인 이메일을 저장소에 쓰지 않는다** | 공개 저장소입니다 |

# 6. 막혔을 때

## 6-1. `git pull` 하니까 충돌(conflict) 났다

같은 파일을 두 사람이 고친 것입니다. **혼자 풀지 말고 Git 아는 사람을 부르세요.**

급하면 이렇게 피합니다:

```bash
git stash          # 내가 고친 것을 잠깐 치워 둔다
git pull           # 남의 것을 받는다
git stash pop      # 내 것을 다시 꺼낸다
```

그래도 충돌이 나면 그때 도움을 청합니다.

## 6-2. `git push` 가 거부됐다

```
Updates were rejected because the remote contains work that you do not have
```

남이 먼저 올린 것입니다. `git pull` 하고 다시 `git push` 합니다.

## 6-3. 내가 뭘 고쳤는지 모르겠다

```bash
git status     # 어떤 파일을 고쳤는지
git diff       # 무엇을 고쳤는지 (q 로 나감)
```

## 6-4. 다 망쳤다, 되돌리고 싶다

**아직 커밋 안 했으면** — 고친 것을 전부 버리고 마지막 상태로:

```bash
git checkout .
```

> ⚠️ 되돌릴 수 없습니다. 살리고 싶은 게 있으면 먼저 복사해 두세요.

**이미 커밋·푸시했으면** — Git 아는 사람을 부르세요.

## 6-5. `npm run dev` 가 `Cannot find module` 오류

`.next` 폴더가 깨진 것입니다.

```bash
rm -rf .next
npm run dev
```

# 7. 어디에 무엇이 있나

```
app/site        현장 화면
app/plant       레미콘사 화면
app/driver      기사 화면
app/api         서버 — 카카오 길찾기·기상청·AI 배분·주소 검색

lib/rules.ts    시방·KS 규칙 (숫자는 전부 여기 상수로만)
lib/ai/         배분 최적화 · 지연 예측 · 긴급 매칭
lib/store/      저장소 — local(브라우저) · remote(Supabase)
lib/services/   외부 API · 시연 시계 · 사진
components/     화면 공용 부품

tests/          자동 테스트
supabase/       DB 구조(migrations) · 초기화 스크립트
docs/           시연 매뉴얼 · 진행 보고서 · 이 문서
```

더 자세한 것은 `README.md` 와 `CLAUDE.md` 에 있습니다.
